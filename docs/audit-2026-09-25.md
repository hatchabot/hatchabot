# Audit — 2026-09-25 (29th audit): Telegram and Discord security

Asked for: "a security audit for telegram and discord". Scope: everything a
bot token touches (at rest, in the seed, in events and logs, in the app and
the CLI, in the management chat's tools), the doors (DM policy, allow lists,
rooms and groups), pairing and the first-message claim, memberships and
revocation, the Telegram and Discord bot pools, cross-owner boundaries, and
the shell and SQL that run on an agent's volume. Four independent reviews ran
over the code (Telegram path, Discord and connectors, pairing and doors,
secrets and logging); every finding below was verified in the code before it
was fixed. Fixed in v2.73.0.

**Verdict: two majors and three mediums, all fixed; the rest are lows fixed
or documented. No token reaches an API response, an event, a log line or the
management chat; every value that reaches a script on a volume is
shape-checked first; every channel route is owner-gated; the door rests at
`allowlist` once anyone is admitted.**

## Findings

### Major
- **The owner's first-message claim was "whoever writes first".** A new bot
  (or a channel added to an agent) opened a 20–30 minute window in which the
  first pairing request was bound as the OWNER's identity — with no check on
  who it was. A Discord bot is visible to a whole server, and a recycled
  Telegram pool bot had just written "this bot is now X" to its previous
  agent's regulars, so a stranger's or a family member's first message could
  become the owner's identity, seed every agent the owner made afterwards,
  and (Telegram) receive the owner's password-recovery links.
  Fixed: Discord and Slack open no window — the owner's identity is taken
  from any agent they are already linked on, else their own first DM shows
  up as a request they approve with *That's me* (the app says so). Telegram
  keeps its window for a brand-new bot, but an id this machine already knows
  as somebody (a member anywhere, another account's link) or a regular of
  the recycled bot is never claimed, and only a well-formed id is ever bound.
- **A Telegram bot survived in the config after a swap or an archive →
  restore.** The writer merged one account key into `channels.telegram.accounts`;
  the previous bot's key stayed on the volume, and after the rebuild both this
  agent and the bot's next agent polled it (the split-answer fault of
  2026-09-24, on two more paths). Fixed: the whole accounts object is written,
  replaced, on every build.

### Medium
- **Removing Discord or Slack left OpenClaw's own approvals on the volume.**
  The rebuild rewrites the config allow list from memberships, but OpenClaw
  also unions in its own store (the 2026.9 allow rows, the 2026.7 credentials
  file). Every Discord and Slack bot sits under the same account key, so the
  next bot attached admitted the people the owner had dropped, with no
  membership to show for it. Fixed: detaching a channel (Telegram too) scrubs
  that channel's allow rows, pending requests and credentials file.
- **A room with nobody admitted was open to everyone in it.** OpenClaw reads
  a room entry without `users` as "anyone in this room"; room mode chosen
  before the owner had linked wrote exactly that. Fixed twice: the app refuses
  room mode until someone is linked, and the writer writes a room with no
  admitted people closed.
- **A failed seed's text reached members.** The rebuild-failed event carried
  the seed's raw output (from v2.72.3, stdout too), and `GET /v1/events` shows
  it to every member of the agent. The seed never echoes values, but the CLI
  might echo a rejected one. Fixed: every token-like value of the spec is
  redacted from the failure text before it becomes an event.

### Low (fixed)
- Token-checking routes (park a bot, add a bot, add a channel) were an
  unthrottled oracle for anyone with an account here. They share the login
  throttle now; a refused token counts like a wrong password.
- The machine owner's `GET /v1/bots/:username/token` reached other people's
  pasted bots and private spares. It answers only for the house's bots and
  the caller's own now; the owner's `GET /v1/agents/:id/bot-token` is logged
  like it.
- An imported `.hatchabot` file's token was stored unverified, so a file
  could name someone else's bot with a junk token. The app checks it with
  Telegram and requires the username to match.
- Two attaches racing past the "already connected" check could bind one bot
  to two agents. A unique index on (kind, account) is the last check; the
  route answers 409.
- A bot taken from the shared Discord pool became the private bot of whoever
  used it last when removed. It goes back to the shared pool.
- A spare Telegram bot's token pasted by hand bypassed the pool and left its
  row unleased (the next lease of it then failed an agent). Refused with a
  pointer to the pool.
- A 409 for a bot another owner's agent runs named that agent. It names only
  the caller's own agents now.

### Documented, not changed
- **Telegram room mode is "everyone in that one group, by @mention".** The
  Telegram group entry has no per-user list (Slack and Discord rooms do);
  the blast radius is the one group the owner picked, and the app's wording
  says so. A per-user list on Telegram groups is a possible follow-up.
- **`hatchabot … --bot-token` on the command line** is visible in `ps` and
  shell history; the interactive prompt is the safer path.
- **A remote runner over plain `tcp://`** would carry the seed (token inside)
  in clear; `ssh://` is the documented transport.
- **Knock flooding**: with *anyone can knock* on, or on a channel with nobody
  admitted yet, every distinct sender's knock reaches the owner's phone once.
  Bounded by distinct platform accounts; a per-agent cap is a follow-up.
- **Passphrase keys use a static-salt scrypt**, and a backup set copies the
  key file beside the database (0600 in 0700). Known and accepted for a home
  machine.
- **Upgraded volumes**: list/deny read the 2026.7 file first when it exists.
  The 2026.9 migration removes the file, so no live volume has both.
- The `ChannelConnector.hosts` field (an egress allow list) is declared and
  filled but not consumed; harmless (channels are refused for the ops agent).

## Checked and sound
- **Tokens**: AES-256-GCM per ref at rest; API responses are field-by-field
  allow lists (`publicChannel`, `publicDiscordBot`, `publicAgent`); event
  details carry kind and account only; `describeConfigCommands` masks stdin
  pipes, batch payloads and the value slot; connector errors are static
  strings; the seed dir is 0700, `--network none`, deleted in `finally`;
  cookies are httpOnly + SameSite=strict in all three auth modes.
- **Authorization**: attach, detach, swap, recheck, rooms, pairing list,
  approve, deny, grant, revoke, allow-knocks, invites, Files, export and the
  console proxy all use `ownedAgent` (owner id equality); members get
  read-only surfaces; other users get 404. Pool leases are `owner_id IS NULL
  OR owner_id = ?`; sharing a bot is the machine owner's alone.
- **Injection**: every channel id, pairing code, account key and kind is
  regex-gated before it reaches a `node -e` script (values embedded via
  `JSON.stringify`, statements parameterised); `docker exec` takes argv
  arrays; Telegram and Discord names from `meta_json` reach only
  parameterised SQL, argv text and a push sent without parse mode; the app
  escapes every bot name, server name, warning, username and first name.
- **Doors**: `allowlist` once anyone is admitted unless *anyone can knock*;
  `pairing` only while empty, knocking or a window is open; the five-minute
  sweep re-asserts it; rebuild regenerates `allowFrom` from active
  memberships; revoke scrubs the credentials file, the sqlite allow rows and
  the config in one script before flipping the row; invitee windows carry
  the invited handle; invite codes are ~49.5 bits, 48 h, single use.
- **Management chat**: no tool takes a token; channel tools call the
  owner-scoped routes with the caller's own credentials; mutations require
  confirmation; viewers cannot mutate.
- **Recovery links**: 128-bit code, 15-minute life, single use, one send per
  username per five minutes, sent only through a bot the id already talks
  to. The binding weakness was the claim window above.
