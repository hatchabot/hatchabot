## Findings

### Major
- **Browser uploads called a helper that does not exist** (`authHeaders()`), so every drop or Upload… failed with a ReferenceError; only `hatchabot put` worked. The page's auth is the session cookie; the call now sends none. *A live test of the CLI path had passed; the browser path had not been exercised.*

### Medium
- **No way back across the 2026.8 line.** Moving an agent onto 2026.8+ migrates its state database (v1 → v23), roster and auth store; pinning or unpinning it back onto a 2026.7 image was accepted and would have failed the rebuild — or worse. The PATCH now refuses with the reason; the way back is the copy downloaded before the move.
- **Console on 2026.9 behind an HTTPS front (found live: History Teacher).** The console proxy forwarded the browser's own hop headers (`X-Forwarded-For`, `-Proto`, `Forwarded`, `X-Real-IP`, `Via`) to the agent's gateway; 2026.9 refuses gateway-authenticated routes carrying forwarded claims from an untrusted address. Those headers never belonged to that hop; they are stripped now on every version, with a test against a fake gateway.

### Low
- An abandoned Files download killed only the docker client; the one-shot kept streaming into the daemon's log until done. One-shots are named and removed when the reader goes away.
- Upload: a directory under the target name received the file *inside* it; refused now. The "not into .openclaw" rule was applied to the requested path, not the resolved one — an agent-made symlink could route an upload into its state (still inside the volume, but harm to itself); the resolved directory is checked too.
- The upload body limit (272 MiB, the import cap) was below the promised `HATCHABOT_FILE_MAX_MB`; it follows the larger of the two.
- A newline in a file name split a listing record; entries are NUL-separated now, and sorted A→Z.
- 2026.8+ images: a Slack/Discord plugin already on the volume was never reinstalled when the image's baked version moved (the same drift brave's `--force` addressed); reinstalled when the versions differ.
- Bulk actions listed the Hatchabot manager; a bulk stop or model switch would have taken the fleet's operator down. Excluded, with a note.

### Sound (checked, no change)
- Files: `cleanRelPath` + `realpath -e` + the home-prefix check inside the one-shot; every path single-quoted; `tar` does not follow symlinks; reads on `:ro` mounts with no network; `downloadName` strips everything but `[\w.+-]`, so no header injection; inline responses carry `CSP: sandbox`, `nosniff`, `no-store`; all routes owner-only; uploads under the busy guard shared with export/restore/rebuild.
- Rebuild concurrency: the resizable semaphore is correct under raise and lower; the route is owner-only and bounded; the config reads the live value.
- The 2026.9 port: every seed shell is static text; the heal is idempotent and precedes the first CLI call; doctor passes are optional; seeds run without network under the long timeout; `models auth --agent main` only on 2026.8+.
- Embedder memory guard: restarts only idle and above 80%; provisioning refuses an engine-free image before recording a switch.

## Operations this round
- The memory search engine reached its 2 GiB cap twice under re-index storms (six agents at a time moving to 2026.9, each re-indexing memory and, on 2026.9, session transcripts). On the Spark the cap is now 4 GiB (`HATCHABOT_EMBEDDER_MEMORY=4g`), the engine's physical batch is 512 instead of 2048 (its compute buffers were the growing part), and rebuilds run three at a time. High CPU on the engine during such a move is the work itself.
- Known flaky test: `test/inviteOnlyDoor.test.ts` "only that @handle or id is claimable" fails about one full run in ten and passes alone; a timing assumption to fix in its own change.
