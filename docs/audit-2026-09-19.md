# Audit, 2026-09-19 (the 19th)

Covers **v1.16.0 → v1.31.3**: the management (ops) agent and its jail, proposals,
the sheet-style UI, web-only agents, Slack and Discord, the unread mark, the
image-build fixes, and the docs/site refresh. 87 files, about 8,200 added lines.

What was done:

- Read every route added since the last audit and checked its access control.
- Read the new modules end to end: `src/ops/*`, `src/channels/{connector,slack,discord}.ts`,
  `src/mgmt/{restTools,coverage,proposalNotifier}.ts`, `src/orchestrator/{unread,buildFailure}.ts`.
- Looked for the classes of bug earlier audits found: shell interpolation,
  unescaped values in the page, unguarded response shapes, secrets in logs or
  exports, routes that skip the owner check.
- Drove every new screen in a stubbed browser and collected JavaScript errors.
- Inspected the running system read-only: container networks and privileges,
  listening sockets, file permissions, backups, and 719k lines of service log.
- `npm audit`: 0 vulnerabilities. No new dependencies since v1.16.0.

## Live (do this first)

**1. 42 of 45 running agents are still on the old shared Docker network.**
- **Where:** the running fleet, not the code.
- **What:** the 18th audit moved agents to `hatchabot-agents` (inter-container
  traffic off) — but only new and rebuilt agents get it. Three agents have
  moved; the other 42 still sit on the default bridge, where each can open a
  connection to another agent's OpenClaw gateway port. Each gateway still
  demands its own random token, so this is defence in depth, not an open door.
- **Fix:** Settings → Fleet → **Rebuild all** (memory is kept). Then re-run the
  check below; it should print 0.
  ```sh
  for c in $(docker ps --format '{{.Names}}' | grep -E "^hatchabot-|^agentclaw-"); do
    docker inspect "$c" --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}' | grep -q hatchabot- || echo "$c"
  done
  ```

## Medium

**2. The channel panel trusted the server's answer.**
- **Where:** `web/index.html` — `v2LoadChans`, `openChanSetup`, `loadDerivedImages`.
- **What:** the Messaging tab did `r.channels.find(…)` and the setup sheet did
  `chanFields.find(…)` on whatever came back. An older server, a proxy error
  page or a partial answer threw inside the sheet render and left the tab
  blank, with the error only in the console. The same shape of bug as the
  `r.pending.map` one fixed during the proposals work; the sweep found a third
  instance in the derived-images list.
- **Found by:** driving every new screen in a stub with error capture.
- **Fixed:** every one of those reads is now `Array.isArray`-guarded, the
  set-up sheet says so plainly instead of opening empty, and the sweep is clean.

**3. Slack and Discord vanished silently when an agent was exported or moved.**
- **Where:** `src/orchestrator/transfer.ts` (unchanged) and the app's confirms.
- **What:** an export carries the agent's Telegram bot; Slack and Discord
  connections belong to apps in the owner's own workspace, so they can't
  travel. Nothing said so: "Move to another cluster" quietly produced an agent
  that had lost a channel, and the old copy was already stopped.
- **Fixed:** Download and Move now name the channels that will not travel and
  where to set them up again. (Carrying them is possible later — it would mean
  exporting the app credentials, which is exactly what a shared template must
  never contain.)

## Minor

**4. The management agent's proxy had no limit on open tunnels.**
- **Where:** `src/ops/opsServer.ts`.
- **What:** each CONNECT held a socket with nothing bounding how many. A
  confused (or hijacked) management agent could hold the box's sockets open.
  It could not reach anything new — the host allowlist is unchanged — so this
  is resource exhaustion, not access.
- **Fixed:** at most 24 tunnels at a time (`HATCHABOT_OPS_MAX_TUNNELS`),
  freed when either side closes; over the cap the proxy answers `429`. Tested
  with a dialer that never connects, so the test touches no network.

**5. A deleted agent left rows behind.**
- **Where:** `src/store/store.ts`.
- **What:** `agent_seen` (unread marks) and `member_identities` (Slack and
  Discord identities) were keyed by agent id and never deleted. No leak — ids
  are UUIDs and are never reused — but the tables only grew.
- **Fixed:** both are cleared when an agent reaches DELETED, with a test.

## Posture (the machine, not the code)

- **Ollama listens on every interface** (`*:11434`, no authentication). Agents
  reach it at `172.17.0.1:11434`, which only needs the Docker bridge. Anything
  on the LAN can use the model server today. Worth binding it to the bridge
  (`OLLAMA_HOST=172.17.0.1`) or firewalling the port.
- **An unidentified process listens on `0.0.0.0:4000`** (IPv4 and IPv6). It is
  not Hatchabot (that is pid 1004276 on 8080) and not a container. Worth a
  look: `sudo ss -ltnp | grep :4000`.
- **The control plane listens on `0.0.0.0:8080`** — deliberate (Tailscale plus
  LAN) and it demands Google sign-in, but it does mean the whole LAN can reach
  the login page. Unchanged from previous audits.

## Checked and sound

- **Every new route is access-checked**: `ownedAgent` for the channel routes,
  `visibleAgent` for the unread mark, `ownerIdOf` for proposals and the ops
  agent. `/v1/channels/*` are behind the normal session. The only exempt paths
  are still the invite pages, the OAuth callback, the agent-to-agent consult
  and the chat's own MCP door — which is loopback-only and compares its
  one-turn token with `timingSafeEqual`.
- **The ops key** is hashed in the database, checked per request, refused
  unless the agent is RUNNING, PROVISIONING or REBUILDING, reminted on every
  build, and deleted on archive or delete.
- **The jail holds**: `hatchabot-ops` is `internal=true` with ICC off, the ops
  server binds the jail's gateway address only (`172.19.0.1:8091` — confirmed
  in `ss`), the agent's container publishes no ports, and the proxy passes
  only CONNECT to port 443 on the AI provider's host (plus Telegram when it
  has a bot).
- **Approvals can't be faked by the agent**: the proposal cards go through
  Hatchabot's own bot, taps are operators-only, and `claim` refuses a record
  that belongs to another account.
- **Secrets**: Slack and Discord tokens are stored like every other credential,
  never returned by an API, marked `sensitive` in config commands (so the
  build log masks them), and deleted with the channel or the agent. A scan of
  719k service-log lines found no token-shaped strings.
- **Shell safety**: every script Hatchabot runs inside a container interpolates
  only constants or `JSON.stringify`-quoted values, and the member-revoke
  script refuses an identity that isn't the plain shape its platform issues —
  tested against a real file for all three channels.
- **The page**: the only unescaped interpolation in the new UI code is a fixed
  label constant; agent ids still go through `jsq()`.
- **Containers**: none privileged, none mounting the Docker socket, no added
  capabilities.
- **Backups** ran nightly through 2026-09-18 and the timer is armed; the data
  directory, the database and `.env` are `0600`/`0700`.
- **Web fetches** the management agent can make (`web_search`, `read_result`)
  still refuse private addresses on every redirect hop, send no credentials,
  and cap the page. The DNS-rebinding window between the check and the fetch
  remains, as noted in the design: worth closing if this is ever exposed to a
  less trusted agent.
