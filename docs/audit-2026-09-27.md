# Audit — 2026-09-27 (30th audit)

Asked for: a comprehensive audit after the week's additions, over everything
since the 28th audit (v2.60.0 → v2.86.2): rootless Docker per tenant and the
shared-host bed, the memory service's guest keys, hibernation, the runtime-pin
clearer, managed mode, the CLI's confirmations, the one-rule AI-source switch,
the pairing store, pools, members, transfers, the unattended scripts, and the
cloud provisioner's first cut. Six area reviews ran in parallel against one
brief (threat model, what counts as a finding, output format); every finding
below was verified in the code — or, where it could be, on the Spark — before
it was fixed or filed. Fixed in v2.87.0 (product) and the same day in
hatchabot-cloud (`bin/hc`).

**Verdict: no critical. Twelve majors, all fixed: three in hibernation (the
wake poll could not see mail behind its bedtime mark; wakes ignored moved-away
and busy; a rebuild left a sleeper's mark on a running agent), two in the AI
source rules (delete and unshare ignored what a container still runs), two in
the memory service (a queued start undid an owner's Stop; two failed rebuilds
locked the running container out), three in the provider (a failed daemon
probe cached for life; usage stats blind to a tenant's prefix; loopback peers
trusted under rootless), two claim windows on one agent clobbering each other,
and — in the scripts and the provisioner — a candidate gate that could not
pass since v2.60.4, colliding tenant ports from slot 11, a firewall that did
not survive a reboot, a create with no rollback, a resume that left agents
stopped, and a test bed that deleted the VM it was told to reuse. One major
was withdrawn on verification (the orphan-doorman eviction: Docker's
`publish=` filter does match the host port on this daemon).**

## Fixed (v2.87.0)

### Hibernation (area C)
- **Mail behind the bedtime mark was invisible.** `getUpdates` with no offset
  answers earliest-first; with `limit=1` the poll returned the marked update
  for ever and ten newer messages behind it never woke the agent (until
  Telegram expired the mark a day later). The poll asks for a page and takes
  the newest id; mail is anything newer than the mark.
- **Wakes ignored "moved away" and "busy."** A sleeper moved to another
  machine was polled every 20 s and started locally on the first message (two
  gateways on one bot token); a sleeper mid-move could be started under the
  export. The poll, the Wake button, a console open, an ask and a consult all
  leave a moved or busy agent alone.
- **A rebuild left the sleeper's mark on a RUNNING agent** (shown ASLEEP,
  swept back to sleep within minutes). Every transition to RUNNING now ends
  the sleep, in the store, whichever path made it.
- One wake at a time per agent (a second ask, the console's first requests
  and the sweep await the same start); one sweep at a time; a start that fails
  three times in a row gives up with a reason on the trail instead of
  4,000 attempts a day; a bot token Telegram refuses is said once and not
  polled again; the record is written before the container is stopped (a
  crash between the two used to leave a stopped agent nothing woke); the idle
  sweep counts an ask or a consult in flight as busy and re-checks right before
  the stop; a consult wakes a sleeping peer; the management agent never
  sleeps, and by hand the scheduled-task rule applies too.
- The boot pin sweep waits for each gateway (three at a time) and puts a
  failure on the trail; the wait polls every 5 s, not every second.

### AI sources (area E)
- **Deleting a source ignored what a container still runs.** "In use" counted
  the source an agent WILL use; a switch without `--now` left the old source's
  token in the container, and the source could be deleted under it. Applied
  sources count too.
- **Unsharing was enforced only at selection.** A later rebuild materialised
  the un-shared owner's token into another account's container. The build
  re-checks: an agent on a source that is neither its owner's nor shared fails
  the rebuild with a clear reason.
- `hatchabot ai … --now` says "the switch is recorded" when the rebuild is
  refused; `embedder guest-rm` asks y/N; a y/N on a closed stdin says "pass
  --yes"; the frozen-model heal in the seed is guarded like its siblings;
  the managed-mode support link is only rendered for http(s) URLs.

### Memory service (area B)
- **A start that landed after an owner's Stop undid it.** `restart()` was a
  stop and a separate un-gated start; the memory-pressure restart and any
  owner's rebuild took that path. Restart is one turn that re-checks the Stop;
  a build brings an enabled-but-down service back only if it is still enabled
  when its turn comes, and fails rather than undoing a Stop.
- **Two failed rebuilds retired the running container's key.** The previous
  hash is now the last ACCEPTED key through as many failed builds as it takes.
- Stop writes its record only once docker has stopped the containers; a
  non-string guest name is a 400, not a 500; guest removal uses `hasOwn`;
  blank usage-sampler knobs mean the default, not zero workers.

### Provider and auth (area A)
- **A failed `docker info` was cached for the life of the process.** Asked
  before dockerd was up (a tenant's reboot, a Mac's login), rootless or
  Desktop read as root Docker for good. Only an answered probe is kept, and
  the user unit orders itself after docker.
- **`stats()` ignored `HATCHABOT_PREFIX`**: a tenant's usage view and the
  engine's memory guard were blind. It filters by this install's prefix.
- **Under rootless, agent containers are loopback peers.** Their requests
  arrive from 127.0.0.1, so the first-account bootstrap skipped the setup code
  and the throttle trusted forwarded-for. Detected at boot (or set with
  `HATCHABOT_CONTAINERS_ON_LOOPBACK=1`): loopback is not "this machine" then.
- Import and restore spawns get the same kill timer as the other docker I/O.

### Pairing and members (area D)
- **Two claim windows on one agent clobbered each other.** One row per agent
  meant the owner's first-contact window and an invitee's shared it; the first
  to bind closed the other's window and shut the door to allowlist, so the
  second person's message was dropped in silence. Windows are one per person
  and channel; the door closes only when no window is left.
- "That's me" refuses a Telegram id that is another owner's member or another
  account's link (it would have handed them the owner's seat and recovery
  links). The stranger sweep denies one at a time per agent. A fixture with
  the maintainer's handle is gone.

### Scripts (area F)
- **`candidate-gate.sh` could not pass any image since v2.60.4**: a variable
  its devices step reads was deleted in that release. Restored.
- **`shared-host-test.sh --vm <kept>` deleted the VM at exit.** `--vm` keeps.
- `install-service.sh` ended in `status | head -5` (SIGPIPE under pipefail:
  the install died before linking the CLI); the guard now forbids `| head -N`
  anywhere, and the two other scripts that had it are fixed.
- `HATCHABOT_YES=1` (or no terminal) takes the recommended sign-in instead of
  reading the caller's next line; the final "Next steps" prints the real port.
- `uninstall.sh`: the CLI's token and channel pin (the USER's, shared by a
  production checkout beside a test one) go only with `--purge`; `--purge`
  refuses when the database is there but unreadable (it would have orphaned
  every volume).
- `upgrade.sh` and `deploy-release.sh` take a lock (the channel timer and a
  hand-run upgrade raced each other's `node_modules.prev`); that directory is
  gitignored so an interrupted upgrade no longer blocks every later one.

### Cloud provisioner (`bin/hc`, same day)
- Ports: Hatchabot 8100+N, management door 8300+N, memory door 8500+N —
  ranges that never meet (8090+N and 8190+N collided from slot 11).
- The firewall is a file `nftables.service` loads at boot, regenerated from
  the registry on every create and remove; the memory door is walled unless
  the tenant serves a guest.
- Create writes the registry row first (`state: creating`), refuses a name
  whose user already exists, and validates every operator argument; the owner
  token goes into the CLI's env file (mode 600), never on a command line.
- Suspend remembers the running agents; resume starts them. Remove revokes a
  guest's key on its host tenant, waits for the user's processes and only
  deletes the row when `userdel` succeeded. The registry is read under a lock
  and a dead transport is an error, not an empty registry.
