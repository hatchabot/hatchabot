# Audit — 2026-09-17 (17th): the user interface

Asked for: exercise the interface itself — the buttons, tabs, dialogs and
settings — rather than the code behind it.

## How it was tested

A driver loads the **real `web/index.html`** in headless Chrome with the API
stubbed (every `/v1/*` route answered with a plausible shape, and the responses
recorded), then:

1. opens **every `<dialog>`** the page defines (29 of them),
2. visits **every Settings tab** (10),
3. fills every input, ticks every checkbox and selects the first real option in
   every `<select>` — so a button is judged on its job, not on an empty form,
4. fires **every `on*` handler in the document** (283 controls in total),
5. records, per control: thrown errors, console errors, unhandled rejections,
   the requests it made, how many DOM mutations it caused, and whether a dialog
   opened or closed.

A control counts as *inert* only if it did none of those things. Counting
requests alone would call every tab button and every dialog-opener dead.

The driver lives in the session scratchpad rather than the repo: it depends on
Docker and a browser, so it is a tool to re-run deliberately, not a CI gate.

## Result

**283 controls exercised, 0 runtime errors** — no exceptions, no console
errors, no unhandled rejections, in any dialog or tab.

The one error the first run reported (`pairs.map is not a function`) was the
harness's own fault: the stub returned `{pending: []}` where the real
`/v1/agents/:id/pairing` returns an array. Corrected in the stub, not the app.
Six more "failures" in an early run were also artifacts — the driver opened
dialogs with `show()`, so the app's own `showModal()` then threw.

## Finding: buttons that refuse in silence (medium)

Eight action handlers returned early when a precondition wasn't met, saying
nothing. Clicking "Apply" with no agent ticked did nothing at all — which reads
as a broken button, and was the one real class this sweep turned up.

| Handler | Was | Now |
|---|---|---|
| `faApply` (Bulk actions → Apply) | silent | "Tick at least one agent first." |
| `moveAgentsApply` (Switch & rebuild) | silent | "Tick at least one agent to move." |
| `moveAgentsApply` (no dialog state) | silent | "Reopen this dialog and try again." |
| `runMigrate` (Migrate & rebuild) | silent | names the missing machine, or the stale dialog |
| `bringInSelected` (Bring in selected) | silent | "Tick at least one agent to bring in." |
| `attachConnection` (Attach) | silent | "Pick a connection to attach." |
| `addAgentEnv` (add variable) | silent | "Both a name and a value are needed." |
| `applyModelToSelected` (Apply) | silent | "Reopen this dialog and try again." |

The good pattern already existed next door — `addSetupField` toasts a specific
reason for each refusal — so this was inconsistency, not a missing idea. A
drift guard now fails if any of those handlers grows a bare `return` again.

## Not findings

- **89 controls changed nothing when clicked.** Reviewed individually: close
  buttons on already-closed dialogs, agent-name deep links (navigation is
  stubbed), and tab buttons inside the agent editor, which needs an agent
  selected through its real entry point. Artifacts of driving the page without
  the state a person would have.
- **Dead handlers** (an `onclick` naming a function that doesn't exist) are
  already covered by `scripts/check-web.mjs` on every `npm test`, and none
  appeared here either.

## Re-running it

The harness is worth keeping for the next interface change. It needs the
collector (a tiny HTTP server that receives the report by `sendBeacon`), because
`--dump-dom` races a long-running script, and the app's own polling starves a
virtual clock. Both cost an hour to learn; they are written down here so the
next run doesn't.
