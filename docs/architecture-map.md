# Architecture map

Where the code for each part of Hatchabot lives, so a diagnosis can go
straight to the right file. Each feature's HTTP routes are a file in
a folder of `src/api/` (`registerXRoutes`), and its rules a service in a folder of
`src/orchestrator/` (`createX`), which knows nothing of HTTP. The web app's
code is 20-odd files in `web/app/` of up to 1,400 lines each. Do not read
them top to bottom: search for the route string or function name listed
below, then read around the hit.

Conventions used here:

- `src/api/data/backupRoutes.ts` — `'/v1/backups/run'`: routes are written as they appear in their file, quotes included, so a literal search finds the handler.
- Web functions are names of functions in the file in `web/app/` named before them; search for "function name(" to find one. Markup (an element's id or class) is in `web/index.html`.
- A button's or field's action is its `data-on-click` (or `data-on-change`, …) attribute in `web/index.html`, or `onAction('click', 'name', …)` where a script in `web/app/` builds it: search for the name.
- Tests live in the test folder, usually named after the module: `test/budgets.test.ts` covers src/orchestrator/usage/budgets.ts.
- `docs/features.md` explains what each feature does for a person.
- `docs/field-reports.md` explains Report a problem and field reports.
- On each bullet, the names after the path are literal strings in that file: functions, route strings, table names or tool names.

## The service and startup

Hatchabot is one Node process (Fastify, run with tsx) that serves the web app
and the /v1 API, owns a SQLite database, and drives Docker. At start it opens
the database, builds the runtime providers, reconciles every agent's state with
what Docker reports, registers sign-in, then all routes, then starts its timers.
`registerRoutes` in `src/api/routes.ts` registers no route itself: it builds
each feature's service once (their timers start there and end in its
`stop()`), puts the ones others call on the route context (`RouteContext`,
`src/api/routeContext.ts`), and registers each feature's route file in turn,
in the order its hooks need.

- `src/index.ts` — `startReconcileLoop`, `registerAuth`, `registerRoutes`, `ensureOpsServer`, `syncEnvFile`: the boot order; also the TLS options, bind address and the daily posture sweep.
- `src/store/instanceLock.ts` — `holdInstanceLock`, `InstanceLockedError`, `InstanceLockUnwritableError`: one server process per database (HB-1436): an exclusive SQLite lock on an empty `<database>.lock` beside it (beside its real place, so a link to the database finds the same lock), taken by `src/index.ts` before it opens the database and held for the process's life; a second server refuses to start, and a crashed one's lock goes with it. A lock file the server cannot write (one a server started as root left) is refused, never held read only for nothing.
- `src/envCompat.ts` — `applyLegacyEnv`, `defaultDbPath`, `defaultBackupsDir`: old AGENTCLAW_* settings are aliased to HATCHABOT_*; default data locations.
- `src/config/envCatalog.ts` — `ENV_SETTINGS`, `ENV_GROUPS`: every setting in .env, its default and its one-line meaning.
- `src/config/envFile.ts` — `syncEnvFile`, `renderEnv`: rewrites .env into the catalog's layout at start-up, keeping a backup.
- `src/api/routes.ts` — `registerRoutes`, `ApiDeps`, `providerFor`, `ownedAgent`, `ownsLocalHost`, `capProblem`, `holdOnce`, `releaseHolds`, `clearPinsWhenUp`, `owedAfterStart`: the route registry; what follows a start or wake (`clearPinsWhenUp`), run again by the boot's `resumeOperations` for each agent running at the start with some of it owed on its record (`owedAfterStart`: a start a restart cut off, HB-0833; not a template task parked as a clash with another of its name, `NAME_TAKEN_WHY` in `src/orchestrator/lifecycle/provision.ts`), six agents at a time; for one whose own operation is not over, by that operation's end when it starts the agent (`STARTS_IT_AT_ITS_END`), else once it is over (`afterItsOperation`, `operationsOverFor`); ownership checks and the per-person agent cap (its places, `capHeld` and `capHolds`, in `src/orchestrator/lifecycle/capacity.ts`: `claim`, `release`; a request's place goes when it answers, at `onSend`). It builds the shared context once (`const ctx: RouteContext`) and calls each feature file with it (`registerInspectRoutes`, `registerClassRoutes`, `registerModelRoutes`), where its routes stood. What it hands back to `src/index.ts` — `routes.stop()`: the services' timers end at shutdown.
- `src/api/routeContext.ts` — `RouteContext`, `Trace`: what route handlers share, as one type: the dependencies, the ownership checks, the busy refusals (and `isArchiving`), the setup and rebuild queue, the model-change ledger (`recordLedger`, `ledgered`), the 202 of a long change in the background (`waitAsked`, `accepted`, `backgroundError`), a console request held to its browser session (`watchConsoleSession`, `watchConsoleHttp`), a machine known not to answer (`hostKnownAway`) and the services other features call (`settings`: classes, models and memory limits; `sources`: AI sources; `channels`: Telegram, Discord and Slack; `backups`: backups, snapshots and restores; `apps`: apps in agents and data sources; `consoles`: the console and the browser panel). A feature file registers its routes from this and its own imports, never from the registry. Also the words and helpers every feature uses: `MACHINE_OWNER_ONLY`, `AGENT_GONE`, `OPS_ALONE`, `TOKEN_CHECK_THROTTLED`, `NO_COMPRESS`, `IMAGE_TAG_RE`, `escapeHtml`, `queryLimit`, `zodMessage`.
- `src/api/errorHandler.ts` — `installErrorHandler`: how thrown errors become JSON replies.
- `src/store/store.ts` — `Store`, `agents`, `hosts`, `ai_profiles`, `agent_events`, `store_migrations`, `runOnce`: the whole SQLite data layer (one class); its constructor creates the tables (`CREATE TABLE IF NOT EXISTS`), runs the schema steps and the named one-time data steps (`store_migrations`).
- `src/store/folderMark.ts` — `markFolder`, `otherInstallsHere`, `folderMarkPath`, `FOLDER_MARK_SUFFIX`, `BESIDE_DATABASE`, `moveCopyFolder`, `sharedFolderWords`, `sharedFolderFix`: two installs whose databases share one folder, where both keep the same files beside them (HB-1151): each start marks the folder with `<database>.uses-this-folder` (written whole, with the database's permissions, its own temporary files a start left removed first; a folder it cannot write in is said, never a reason not to start), and another mark whose database is there is logged as `data.folder_shared`, with the fix naming what this install's database takes with it to a folder of its own (the files named for it, and its move-copies folder, `moveCopyFolder`, which `src/orchestrator/backups/backupFiles.ts` `moveCopyDir` uses too); a mark whose database is gone, or its own, says nothing. `src/doctor.ts` — `dbSharedWith`: the doctor fails on the same. `scripts/uninstall.sh` `rm_db` removes this install's mark and its temporary files. Tests: `test/folderMark.test.ts`.
- `src/store/rollbackMark.ts` — `takeRollbackMark`, `restampRollbackMark`, `rollbackMarkPath`, `ROLLBACK_MARK_SUFFIX`, `HOLDS_AFTER_ROLLBACK`, `ROLLBACK_DROPS`: a rollback, as the next start finds it (HB-0840). `scripts/upgrade.sh`, `scripts/deploy-release.sh` (their `mark_rolled_back`, in the helpers both read, `scripts/upgrade-helpers.sh`, called just before the restart onto the release gone back to: a rollback after a release that did not come up, a cut-off upgrade's repair, and a release named that is older, `older_release`; the first two only when the record says the release being left was started and nothing went back since, `left_ran`, from the `started` and `back` lines `scripts/restart.sh`'s `said_restarted` writes in the record `HATCHABOT_RESTART_RECORD` names, and on such a rollback the note written before the restart onto an older release named is taken away when the record does not say that release started, `unmark_rolled_back`: one that never did, and one of v2.191.0 and older, whose restart.sh writes no `started`, though it may have run a few minutes: the release gone back to knows every kind of hold it keeps, and serves them minutes late, not days; a note already there when an older release is named, kept for a later release's kinds or after a refused drop, is kept whole in `<database>.rolled-back.prev` and put back by `unmark_rolled_back` in place of removing it, and the record says `noted <time>`, so that a cut-off run's repair does the same, only while the note is the one written then, so never taking away a note put back nor putting the `.prev` back over one written since (a note written with no record, for a release that ran, drops the `.prev`); HB-1455, HB-1456) and `scripts/restart.sh` (when its health wait fails under an upgrade.sh of v2.191.0 and older, `HATCHABOT_UPGRADE_COPY` with no record named, since the upgrade.sh then running is the release's being left, and only on a restart onto the release that upgrade is going to, by its record, `onto_upgrade_target` (its `to` line; a git record from an upgrade.sh of v2.171.0 and older has only `from`, and then any commit but that release's), never on its repair's restart of the release gone back to; never on a restart back, `HATCHABOT_RESTART_BACK`) write the time in `<database>.rolled-back` beside the database the service opens (`rolled_back_note`, .env read as the service reads it with `env_named`, the same function in the helpers, in `scripts/restart.sh` and in `scripts/setup-host.sh`, and on Linux by the rule of the machine's own systemd for a comment that ends in a backslash, `systemd_major`, asked once a run and never taken from the environment, the same in the seven scripts that read .env so: these four, `scripts/backup-volumes.sh`, `scripts/restore-drill.sh` and `scripts/uninstall.sh`, HB-1457; a folder .env names that is not there is said); `src/index.ts` takes it right after the store is built, before anything reads a hold: the holds kept before that time whose kind would change an agent if served late go (`Store.dropAgentHoldsBefore` with `ROLLBACK_DROPS`: model-apply, class-detach, budget-pause; every kind is placed, drop or keep with why, in `HOLDS_AFTER_ROLLBACK`), those kept after it stay (v2.191.0 knows the table, not the note), and the note goes with them, logged as `holds.dropped_after_rollback`, unless a hold of a kind this release does not know (a later release's, gone back from) was kept before it: then the note stays, taken again at each start, for the release that knows that kind (`Store.agentHoldKindsBefore`; `noteKept` in the log); a note whose time cannot be read is taken at its file's own time, and a drop the database refuses is logged as `holds.rollback_drop_failed`, the start going on and the note left for the next one, and until then the holds it would have let go of read as not there (`Store.hideAgentHoldsBefore`, in `agentHold` and `agentHolds`, where every reader reads them). A note written while a process ran (its file's time, to the nanosecond, and the time it holds both after the start: the scripts' advice when they cannot write it gives the rollback's own time, so typed later it is never moved) gets the time that process stops, after its last write (`restampRollbackMark`, in the SIGTERM handler after the database is closed; `holds.rollback_note_restamped`), so what the release being left kept until the restart back is let go of too. Tests: `test/rollbackMark.test.ts`, the restart in the middle in `test/holdsAcrossRestart.test.ts`, and the scripts' in `test/scriptsUpgrade.test.ts`, `test/bundleUpgrade.test.ts`, `test/scriptsFollow.test.ts` and `test/restartProbe.test.ts`.
- `src/store/schemaVersion.ts` — `SCHEMA_STEPS`, `SCHEMA_VERSION`, `checkSchemaVersion`, `applySchemaSteps`, `schemaStanding`, `schemaNewerMessage`, `SchemaTooNewError`, `stepFingerprints`: the database's schema number (`PRAGMA user_version`) and the numbered steps that change tables which already exist, each run once and recorded in `schema_steps` as additive or not (a new column is appended there, never edited in). A start refuses a database newer by a step that is not additive and warns once on one newer by additive steps; `src/doctor.ts` — `schemaLine`, `schemaFacts` report the same. `test/schemaVersion.test.ts` — `RECORDED`, `fingerprintProblems`: fails when a step was edited, moved or removed; `test/fixtures/` holds the databases v1.0.0 and v2.190.0 made, which it upgrades.
- `src/domain/types.ts` — `Agent`, `AgentState`, `AIProfile`, `Host`, `Channel`: the shared record types.
- `src/domain/stateMachine.ts` — `canTransition`, `assertTransition`: the legal agent state changes (PROVISIONING, RUNNING, STOPPED, ARCHIVED, FAILED, ...).
- `src/domain/processAlive.ts` — `processAlive`: whether a pid runs on this machine; used by `sweepOneShots`, the backup lock (`lockHeld`) and the embedder's `clearStaleParts`.
- `test/layers.test.ts` — `RANK`, `KNOWN`: the layers of src/ and the direction they may import in (docs/architecture.md). A lower layer (domain, store, providers, ops, mgmt) never imports the orchestrator or the API; a rule both need lives in src/domain/.
- `src/domain/filesLimit.ts` — `filesMb`, `FILES_MB_DEFAULT`, `FILES_MB_MAX`: the biggest file an agent may send on each app.
- `src/domain/templateParams.ts` — `TemplateParamSchema`, `PARAM_KEY_RE`: a template's parameters, as every path that accepts them checks them.
- `src/domain/derivedImageName.ts` — `derivedNameProblem`: the rule for a derived image's name.
- `src/domain/envPolicy.ts` — `envValueProblem`, `reservedEnvProblem`: which agent environment variables are allowed.
- `src/secrets/localSecretStore.ts` — `LocalSecretStore`: encrypted secrets (bot tokens, keys) in the database, keyed by HATCHABOT_SECRET_KEY.
- `deploy/hatchabot.service` — `ExecStart`: the systemd user unit that runs the service.

## Install and upgrade

The one-line installer downloads a prebuilt bundle (its own Node and
dependencies) where one exists for the platform, and otherwise clones the
repository and installs natively. Release channels (stable, beta) are named in
`channels.json`. Upgrades check out another release and restart the service;
the doctor command prints what is wrong with an install.

- `install.sh` — `install_bundle`, `install_native`, `bundle_room`, `remember_named`, `newest_release`, `in_docker_group`: the one-line installer (`mf_fetch`, `mf_paths`, `mf_matches`: the bundle checked against the release's release-manifest.json, the .sha256 only for releases made before manifests).
- `scripts/release-manifest.sh` — `get`, `asset`, `image`, `load`, `data_dir`, `mf_required`: what a release vouches for — its release-manifest.json, checked and kept in the data directory (release-manifests/), and refused when missing from a release that must have one (v2.159.0 on); the same reader as `install.sh`.
- `channels.json` — `stable`, `beta`: which release each channel points at.
- `scripts/build-bundle.sh` — `PLATFORM`, `linux-arm64`, `darwin-arm64`: builds the per-platform release bundle.
- `.github/workflows/release.yml` — `check`, `attest`, `publish`, `--tagged`: the only way a release is made, on the public repo when the publisher pushes its tag (the tag's commit checked, bundles and image built read-only, manifest, attestation, a checked draft, then publish); `scripts/release.sh` — `refs/tags/$TAG`, `HATCHABOT_PUBLIC_REMOTE`: tags the version commit in the dev repo (`hbt release`); publish.toml (how the publish kit publishes it) and scripts/private-values (its private values; never published); `scripts/release-check.sh` — `newest`, `--wait-ci`, `--tagged`, `--public`: may this commit be released as this version; `scripts/release-manifest.mjs` — `buildManifest`, `validateManifest`, `collectAssets`, `checkAssets`, `openclawFromDockerfile`: `release-manifest.json`; `scripts/oci-index.mjs` — `describeLayout`, `mergeDescriptions`: the runtime image's index digest before anything is pushed.
- `scripts/publisher-copy.sh` — `publisher_copy_check`, `PUBLISHER_COPY_MATCHES`, `PUBLISHER_COPY_SEEN`: is the publisher's copy of publish.toml (projects/<name>.toml in cksci/publisher, which its gate holds every tag to, and which nothing here can read) known to match the commit about to be tagged: the commit's publish.toml is held to the newest release tag's, byte for byte, and a change since, or no release tag at all, stops with what changed, the file to set the copy to and the releases and fast-lane tags still waiting (exit 4) until the caller says the copy matches (HB-1492); a pass warns when that newest tag is not published yet and its publish.toml is not the newest published release's. `publisher_copy_clear` removes its refs (refs/hatchabot-copy/). Sourced by `scripts/release.sh` (`--publisher-copy-matches`, before the privacy steps) and `scripts/promote.sh` (`copy_check`, `HATCHABOT_PROMOTE_PUBLISHER_COPY_MATCHES`: before the promote lands, and in `fast_lane` before its tag).
- `scripts/kit_checks.py` — `load_config`, `OSV_VERSION`, `OPENGREP_VERSION`, `RULES_COMMIT`: the publish kit's dependency and code checks (an unchanged copy of the kit's `checks/kit_checks.py`), run on each pull request by `.github/workflows/kit-checks.yml` (dev repo only); `kit-checks.toml` — `lock_files`, `vuln_exceptions`, `code_exceptions`: what it reads and the exceptions (docs/releasing.md, "The kit checks").
- `.github/workflows/bundles.yml` — `workflow_call`: builds the bundles (artifacts only); `.github/workflows/runtime-image-build.yml` — `workflow_call`, `HATCHABOT_RELEASE`: builds the runtime image (artifacts only); `.github/workflows/runtime-image.yml` — `openclaw_version`: a candidate image; `.github/workflows/promote-images.yml` — `image-aliases`, `allow_backwards`, `plan`: moves `:latest`/`:beta`/`:stable` by a release manifest's digest, on the public repo: `plan` reads which channels a fast-lane push of `channels.json` moved (`scripts/promote.sh` — `fast_lane`: asks the publisher for it).
- `scripts/sqlite-driver.sh` — `better-sqlite3`, `--compile`: makes sure the database driver loads on this machine.
- `scripts/setup-host.sh` — `say`, `launchd`: clone-based setup of a fresh host (dependencies, .env, the service; launchd on macOS).
- `scripts/launchd-plist.sh` — `xml`, `service`, `backup`: the macOS launchd jobs setup-host.sh installs (paths XML-escaped, the install dir an argument); `install.sh`, `scripts/uninstall.sh` — `plist_dir`: read the install dir back out of one.
- `scripts/install-service.sh` — `sed_escape`, `systemctl`: installs the systemd user service on Linux.
- `scripts/systemd-quote.sh` — `systemd_quoted`, `systemd_arg`, `systemd_path`: how a value goes into a systemd unit; sourced by every unit writer: `scripts/install-service.sh`, `scripts/follow-channel.sh`, `scripts/follow-latest.sh` and `scripts/privacy-sync.sh`.
- `scripts/ensure-deps.sh` — `npm ci`, `ABI_STAMP`: installs dependencies only when the lockfile moved; checks the database driver again when Node changes.
- `scripts/upgrade.sh` — `rollback`, `back_to_cur`, `restore_deps`, `restore_prev`, `not_ours`, `remember_channel`, `REDO`, `pin_named`, `unpin`, `PIN_RECORD`, `disk_full`, `no_stage`, `vernewer`, `swap_failed`, `HELPERS_BLOB`, `rollback_bundle`, `restart_back`, `put_back_rec`, `kept_check`, `back_down`, `kept_stop`, `stop_or_go`, `went_on`, `kept_again`, `kept_end`, `KEPT_MAX`, `find_target`, `RECHECK`: the upgrade command (a channel or a tag), with rollback on failure; the release is looked for (`find_target`) before the lock is taken, and the channel it was looked for by (or the timer's, or one named) read again under it (`RECHECK`); a bundle install's next bundle is checked by release-manifest.sh asset, and a bundle swap cut off part-way (its `.swapping` record) is put back at the next start, the previous `scripts/` through `.rollback-scripts` beside it; a restart back onto a release put back that does not come up keeps a record (`restart_back`: `.swapping` rewritten by `restore_prev` into `put_back_rec`'s form, naming no file; the git install's `FROM_FILE` stays), so a later run restarts it again (HB-1456): first it asks once whether it serves now (`kept_check`, restart.sh's `HATCHABOT_RESTART_PROBE`: its page names the version in package.json), and leaves one that does; the record counts the tries to restart it (`back_down`, `tries` lines) and gives up after `KEPT_MAX` (`kept_stop` says how to clear it). Exit 5 (the machine's disk or permissions, never counted against the release) only through `machine_short`; `finish` reads any other 5 as 3. - `scripts/upgrade-helpers.sh` — `machine_short`, `free_mb`, `disk_words`, `said_kind`, `said_path`, `own_place`, `disk_short`, `step_tee`, `step_tail`, `new_step_log`, `run_step`, `step_short`, `put_rec`, `change_failed`, `link_end`, `put_line`, `put_dir`, `put_failed`, `proc_start`, `proc_start_utc`, `started_as`, `lock_left_over`, `take_lock`, `lock_short`, `lock_in_way`, `deps_holder_gone`, `deps_lock`, `deps_unlock`, `kept_tries`, `kept_record`, `checkout_recorded`, `older_release`, `mark_rolled_back`, `systemd_major`, `env_named`, `rolled_back_note`, `left_ran`, `unmark_rolled_back`, `upgrade_helpers_end`: the helpers `scripts/upgrade.sh` and `scripts/deploy-release.sh` share, one file where each kept a copy (HB-0636): how a failed step's words are read (the machine's 5 only through `machine_short`, else the release's 3), the records and folders each writes, the upgrade lock and the dependencies' lock, a release put back that did not come up, and a rollback's note. Definitions only, and sourced by neither: each reads it once at its start, before anything changes, and only the file it was made with, by its git blob id (`HELPERS_BLOB` in each; `test/upgradeHelpers.test.ts` holds it to the file and prints the line to set). upgrade.sh writes it at the head of its temporary copy, from the install's git, else from beside it (once `git hash-object` says it is that file; as it is in a bundle install, whose `scripts/` moves whole); deploy-release.sh `eval`s it from the production checkout's git (any release's follow-latest.sh runs a tag's deploy script as a temporary copy, with nothing beside it), else from beside it once `git hash-object` says it is that file. - `scripts/follow-channel.sh` — `--install`, `--uninstall`, `MAX_TRIES`, `REMEMBERED`, `PINNED`, `repair_due`, `cut_rec`, `kept_record`, `put_back`, `set_aside`: optional timer that keeps an install on the channel chosen last (its `data/channel`; retries a failing install less often, then sets it aside, `set_aside` the same text in `scripts/follow-latest.sh`; a pin is left alone unless an upgrade was killed part-way; upgrade.sh's 6, a release put back that is not up with nothing to upgrade it to, counts no try, and is said by the release its record names, `put_back`; a record kept for it, `kept_record`, is not said to be an upgrade cut off).

- `scripts/promote.sh` — `ci_gate`, `public_ci_note`: asks CI on the dev repo (a gate) and reads the public repo's (said, not a gate).
- `scripts/uninstall.sh` — `--purge`, `--installed`, `volumes`, `other_installs`, `runner_agents`, `drill_is_mine`, `other_databases`: removes the install it lives in (or, with `--installed`, the one the service runs), keeping data unless asked; a purge refuses while agents run on a runner (`--forget-runners`), and takes its data folder whole only when no other database is in it.

## AI sources and Claude login

An AI source (an "AI profile" in code) is a Claude plan via a setup token, an
API key, or a local model server. Each agent uses one source and one model.
Credentials are stored encrypted and written into the agent at provision or
rebuild; a model change on the same source applies live, a source change needs
a rebuild. "Not logged in" after a source switch is usually a session pinned
to the old runtime (runtimePins). The models an agent can switch to are its
source's list, written as `agents.defaults.models` and, on OpenClaw 2026.9 and
later, as the allowlist its model picker offers (`agents.defaults.modelPolicy.allow`);
a model change writes the list before the model, and a change to a source's list

## Creating, provisioning and rebuilding agents

Creating an agent writes its record, then a background task provisions it: a
bot is leased, a runtime spec is built, and the provider runs a one-shot "seed"
script against the agent's volume (OpenClaw config commands, workspace files),
then starts the container and waits for it to be healthy. Rebuild re-runs the
same seed against the existing volume, so memory survives. A seed failure names
the step that failed.

## Data sources: git repos and folders

An agent's data sources are listed under "## Data sources" in its AGENTS.md, by
exact path. A **git repo** is never a mount of your disk: it is cloned onto the
agent's own volume at `/home/node/.openclaw/<name>` (`<name>` is the repo's
name by default). A public repo is cloned over https with no credentials and
pushing is disabled; a private or writable one uses a deploy key Hatchabot
generates, which you add to the repo. The clone is made at provision and
rebuild, and only when it is missing: after that, the agent updates it with
`git pull`. A **folder** is a live, read-only (or writable) view of a path on
the host.

## The runtime provider and Docker (local and runners)

per run: a copy of the database, the secret key, and one archive per agent

### Durable operations (long changes that survive a restart)

A long change records itself in the `operations` table as it goes: what was
asked, the last step done, the outcome, and what the owner may do next. An
agent whose operation is running, was interrupted by a restart, or is held for
a choice is busy on disk: Start, Rebuild, Archive, Move, Delete, Wake and Retry
refuse with its line. At boot, after the first reconcile, each interrupted one
is finished, undone or held by its kind's rule (docs/operations-and-one-interface-design.md, docs/moving-agents.md).

Kinds: move-host, migrate, import (v2.154.0); restore-backup, restore-snapshot,
archive, rebuild, provision, app-install / app-update / app-rollback,
install-image and backup-run (v2.155.0); restore-drill (v2.157.0); adopt-workspace (v2.191.0). A rebuild or a setup is recorded
(`queued` while it waits its turn) but its guard stays in memory
(`BACKGROUND_KINDS`): it refuses nothing on disk until a restart cuts it off.
An image copy, Back up now and a restore drill are a machine's operations (no agent): the
Activity list reads them from the table (`listMachineOperations`).

In the background (v2.156.0): a move (`move-host`), a move to another
Hatchabot (`rehost`), a full-copy import, a backup restore and a snapshot
restore answer `202 { operation }` once validated and begun (`runInBackground`;
a move to another Hatchabot after its preflight), and go on after the answer.
`?wait=1` keeps the old answer. `POST /v1/agents/restore` stays synchronous
unless `?async=1`: the other Hatchabot's migrate reads the agent from its
answer. The page and the CLI follow `GET /v1/operations/:id`; Activity shows
one row per operation (its op.* lines and what it logged meanwhile left out of
the feed, kept in the agent's own timeline).

## Reaching Hatchabot from elsewhere: Tailscale and public access

Off the machine, Hatchabot is reached over Tailscale (Serve gives the app an
HTTPS address on the tailnet). Public access (a Tailscale Funnel to the open
internet) is optional and refuses to serve until its safeguards pass: a sign-in
per person, a second factor for everyone with owner rights, invited people only,
a separate port, sign-in limits and automatic upgrades on the stable channel.

- `src/ops/tailnet.ts` — `tailnetInfo`, `enableServe`, `funnelOn`, `funnelOff`, `funnelStatus`: Tailscale commands. `parseServeStatus`, `serveLeftOnMainPort`, `repointServe`: serve's entries that still land on the app's own port, pointed at the listener for it at each start (HB-1239); `proxyPort`, `serveCommand`, `PROXY_PORT_DEFAULT`: that listener's port and the command for it; `ProxyListenerState`, `listenerNotOpen`: serve is never moved or turned on onto a listener that did not open, and the words that say so.
- `src/api/proxyListener.ts` — `openProxyListener`, `proxyListenerState`, `proxyPortClash`, `proxyPort`, `serveCommand`, `PROXY_PORT_DEFAULT`: the listener `tailscale serve` is pointed at (`HATCHABOT_PROXY_PORT`, 127.0.0.1:8094; the port and the command are passed on from `src/ops/tailnet.ts`), opened in `src/index.ts` after the app's own; the only place `X-Forwarded-For` names the client (HB-1239, HB-1435). `proxyListenerState` is whether it opened in this process, which the setup guide's `serve` reads before it moves or turns on serve. - `scripts/ui-clickthrough.mjs` — `--headless`: the click-through UI test (headless Chrome against the real page). Under its virtual time Chrome draws no frames: no `requestAnimationFrame` callback runs, no ResizeObserver reports and no dialog's close event fires. `window.__frame` (in `RECORDER`) stands in for a frame: the waiting callbacks run, then each ResizeObserver hears of its boxes that changed size.
- `web/app/core.js` — `phoneQuery`, `isPhone`; `web/app/spend.js` — `mpRow`, `mpHead`, `spendChartWidth`, `spendChartFit`, `spendChartResized`, `spendChartsRefit`, `spendChartSVG`, `spendChartWords`, `spendChartsPrune`; `web/index.html` — `.phone-stack`, `.phone-wrap`, `.phone-flow`, `.v2classicmap`: on a phone (640 px wide or less: one media query, `web/app/core.js` `phoneQuery`, read by `isPhone`) rows are laid out for the width: a row of words and buttons (`web/index.html` `.pair` with its words in `.grow`) wraps when its words would be squeezed, the buttons under them (one rule, beside `.phone-stack`, which a task row keeps to put all its buttons under its words), one marked `.phone-wrap` puts its first item (a dropdown or a text box) on a line of its own, a label marked `.phone-flow` keeps its dropdown beside it when they fit and under it when not, more rules sit after `.v2classicmap`; a wide table (`.mp-tbl`, built with `web/app/spend.js` `mpHead` and `mpRow`) is a card per row with each value named after its column (an empty cell unnamed); the cost chart is drawn at the inside width of its card, at most 640, wherever it is (`spendChartWidth`; 640 while its box is hidden); its picture alone (`spendChartSVG`, the agent picker and range buttons kept) is drawn again a frame after its box's width changes (`spendChartFit`, a ResizeObserver, answers with `spendChartResized`, which hands the boxes that changed to `spendChartsRefit`, which reads every width before it draws); a chart hidden then is fitted when it shows; charts gone from the page, or in a dialog that closed and is still closed, are let go (`spendChartsPrune`, at each drawing and refit, and as a dialog closes; a closed dialog's charts go back to "Loading…" until it draws them anew). The tables' alignments are `mpLeft` and `mpNum`. `scripts/ui-clickthrough.mjs` — `phoneEveryScreenFits`: opens every screen at 360 and 390 px with fuller made-up data and fails on anything past the edge, spilling, squeezed, a dropdown cut short beside other things, or chart text under 10 px.
