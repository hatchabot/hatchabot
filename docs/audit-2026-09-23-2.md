# Audit — 2026-09-23, second round (27th audit)

Asked for: "a round of audits/documentation update/security checks" over
what shipped since the 26th audit that morning (v2.40.0–v2.42.2: the memory
search service and its door, the per-agent switch, Resources, View by, the
Loading state). Three reviews ran in parallel; every finding was verified
before it was fixed. Fixed in v2.43.0.

## Findings

### Major (the memory search service)
- **A stopped agent lost its door key.** The key file carried only running
  agents, so stop → start (no rebuild) meant every memory call answered 401
  with nothing on the record. Fix: every existing agent's key stays; archive
  and delete retire it.
- **A rebuild re-minted the key before the new container existed.** The old
  container lost semantic recall for the whole build and, if the build
  failed, for good. Fix: the previous key stays valid beside the new one
  until the build is accepted (`embed_tokens.prev_token_hash`,
  `commitEmbedToken` in `recordApplied`).

### Medium
- **Any account could start the machine-level service** by switching its own
  agent and rebuilding, and keep it enabled past the owner's Stop. Fix:
  provisioning uses only a service the owner turned on; a switch while it is
  off builds the agent on its own engine and puts the reason on its record.
- **The server's key sat in argv** (`/proc/<pid>/cmdline` is world-readable)
  and the engine answered host-originated traffic on its internal address.
  Fix: `--api-key-file` from a 0600 file, the engine runs as the Hatchabot
  user, the door reads the same file.
- **Every never-indexed agent would have run `memory index --force` on its
  next rebuild** — the whole fleet on the next Rebuild all. Fix: only a
  switch, or a shared agent never confirmed, re-indexes.
- **A failed build's decision could be stamped later** by a live model
  change, and skip a needed re-index. Fix: consumed once used, forgotten on
  failure. Moves and imports now carry the service and re-index.
- **`HATCHABOT_EMBED_URL` was documented but only disabled the service.**
  Fix: switched agents are given that server's address, key and model.
- **Resources polled `docker stats` on every machine while any Fleet tab was
  open.** Fix: only while that tab shows; a 3 s cache per machine.

### Low (fixed)
The classic layout never populated the engine row; the machine owner saw other
accounts' agents as "shared with you"; `GET /v1/embedder` showed the external
URL (which may carry credentials) to every account; a failed 90 s health wait
left both containers running unmanaged; a health tick could resurrect a
service just stopped; retired keys lingered in the file; the door counted
requests but not in-flight work; a failed first agent list left "Loading…"
with no message; `top` was inserted inside `list`'s help text.

### Documented, not changed
- The door's per-minute limit and in-flight caps bound abuse from a
  prompt-injected agent; a flood still costs the machine CPU. A byte/input
  budget is a later refinement.
- Agents on runners stay on the baked engine (the door is on the main
  machine); a runner-side door is future work.
- Keys of an archived or deleted agent leave the door's file within one
  health tick (five minutes), not at once.

## Attacked and held
Door: fixed upstream path, no proxying, Host header ignored, unknown paths
404, no/wrong key 401, body cap 413, JSON parsed before forwarding, keys
re-read on change through the directory mount. Engine: internal network,
read-only, no capabilities, memory and pid limits. Second local user:
`<data>/embed` 0700, keys 0600. Runners stay baked. Every `/v1/resources`
interpolation escaped; scoping verified by test for owner and non-owner.
PATCH `embedMode` owner-only and enum-checked. View by: no drag outside
Groups; unknown host/profile labelled, not thrown. Model file: `.part` +
sha256 + rename, the image copy checked too.
