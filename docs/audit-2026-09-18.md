# Audit — 2026-09-18 (18th): security and code

Covers v1.12.3 → v1.15.4: the embedded OpenClaw console (proxy framing,
device pairing, auto-approve, session deep link), agent icons (storage,
AI picking, import/export), and the new home screen (v2), which became the
default in 1.15.0. It also re-checked the surfaces those changes lean on:
the console proxy, container networking, CLI and agent tokens, and
cookies/CSRF.

Method:
- Code review of the diff.
- Read-only inspection of the running system: container networks, OpenClaw's
  security headers, and OpenClaw's gateway source for how pairing requests are
  created.
- Experiments with throwaway containers and a prefix proxy that mimics
  Hatchabot's.
- No production agent's state was changed, and no chat content was read.

## Medium

**1. Agents could reach every other agent's gateway directly.**
- **Where:** `src/providers/localDockerProvider.ts`.
- **What:** every agent container ran on Docker's default bridge network, which
  allows inter-container traffic. An agent that can run shell commands (most can
  — and a prompt-injected one runs someone else's) could open a connection to
  any other agent's OpenClaw gateway at `172.17.0.x:18789`. That bypasses
  Hatchabot's owner-only proxy entirely.
- **Reproduced:** a throwaway container on the default bridge opened a
  connection to the Taco Agent's gateway port. It connected and sent nothing.
- **Why it wasn't worse:** each gateway demands its own random token before
  anything else. OpenClaw rejects a bad token before it would even record a
  device-pairing request (`message-handler`: `if (!authOk) rejectUnauthorized`
  precedes `requestDevicePairing`). This was confirmed in the gateway source.
- **Why it still mattered:** on a multi-account box, the only thing standing
  between one household member's compromised agent and another's agents was
  that token.
- **Fixed:** new and rebuilt agents go on a dedicated network,
  `hatchabot-agents`, created with `enable_icc=false`. Verified with throwaway
  containers:
  - containers on it cannot reach each other;
  - they still reach Hatchabot (`172.17.0.1:8080`, used for agent-to-agent
    calls) and Ollama (`172.17.0.1:11434`);
  - the gateway's loopback-published port still works.
- `HATCHABOT_AGENT_NETWORK=bridge` restores the old behaviour.
- **Existing agents move when rebuilt:** Settings → *Rebuild all*.

## Minor

**2. Agent ids went into the v2 screen's click handlers unescaped.**
- **What:** the classic cards already did this. Ids are server-minted UUIDs,
  so it was latent, not live.
- **Fixed:** `jsq()`/`esc()` throughout the v2 screen, as was done for account
  ids in the 16th audit.

**3. The home screen dropped keyboard focus every few seconds.**
- **What:** the poll rebuilt every icon even when nothing had changed. That
  moved focus off the icon a keyboard user was on, and could strand a tooltip
  over an icon that had just been replaced.
- **Fixed:** the grid is only re-rendered when its markup changes, and focus
  is restored when it does.

**4. "Let Hatchabot pick" blamed a missing AI when the AI was merely busy.**
- **What:** a rate-limited management source falls back to the keyword table,
  which is the right call, but the message said none was set up.
- **Fixed:** the message now covers both cases.

## Checked and sound

- **Console proxy.** OpenClaw's strict CSP is passed through: `script-src
  'self'`, no inline script, `object-src 'none'`, `base-uri 'none'`, plus
  `nosniff`. Only `frame-ancestors` is relaxed, to `'self'`. The Hatchabot
  session cookie is still stripped before a request reaches the gateway.
- **Console auto-approve.** It approves requests from the last ten minutes,
  for the agent's owner, while the panel is open. Since a pairing request
  can't exist without the gateway token (finding 1), a third party can't use
  it to slip a device in.
- **Console session link.** The slug is URL-encoded into
  `chat?session=agent:<slug>:main`. OpenClaw's agent id is always the slug
  (`configWriter` adds agents by it), and a guard test holds that together.
- **Icons.**
  - `PATCH` validates one emoji (ASCII refused, one grapheme) and `#rrggbb`.
  - The AI's reply is filtered down to exactly that, so text in an agent's name
    or description can't smuggle anything through.
  - Imports re-validate, and a bad value is dropped, not fatal.
  - `/icons/auto` only touches the caller's own agents.
  - One run per owner at a time.
- **Tokens.** Agent-scoped A2A tokens still can't authenticate as an owner
  (`agent_id IS NULL` in `ownerForCliToken`), so they can't reach the icon
  routes or anything else new.
- **Cookies/CSRF.** Session cookies are `httpOnly` and `SameSite=Strict`, so
  the v2 chat's arm-on-send can't be triggered cross-site. Every change still
  arrives as a card needing Confirm.
- **v2 rendering.** Every value interpolated into markup is escaped, or is
  structurally safe: Telegram links are always `https://t.me/<username>` from
  `getMe`; toasts use `textContent`; icon colours are regex-checked before
  reaching a `style`.

## Observations (not defects)

- **The console runs on Hatchabot's origin.** That's what lets it be embedded,
  and it was already true of the new-tab console before 1.13.0. OpenClaw's CSP
  limits what an injection inside it could do. A separate origin (a second
  port) would remove this class entirely, but browsers would then treat it as
  third-party for storage. Worth doing if the console ever renders content
  more freely.
- **The console shows the agent's shared DM session.** OpenClaw's default is
  one DM session per agent, so when members also talk to an agent, its owner
  sees those turns in the console. That is no new exposure: the owner could
  already download the full chat history. People sharing an agent should know
  it.
